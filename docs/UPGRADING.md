# 从早期私有整合版升级

这是迁移检查表，不是可在任意手机直接执行的覆盖安装器。当前 GitHub 上传不操作手机。

## 为什么不能直接覆盖后再启动

旧版可能有独立启动的 serve/pipeline/watchdog，以及绕过状态机的维护/恢复入口。它们没有新实例登记，控制器会将其报告为 unmanaged。新旧两套同时运行可能互相拉起服务或操作 USB。

先核对当前已运行版本、权限、目标路径与保存的数据；车端结束录像并备份重要内容。在可中断环境按已有版本的身份记录受控停止旧实例。没有可信登记的进程不能由名字或旧 PID 猜测终止，需单独核实。不要用全局 pkill 来迁移。

## 文件与配置

1. 备份实际要替换的文件和原始元数据，包括 mode、uid/gid、SELinux xattrs；不收集凭据到 GitHub。
2. 九个 `controller/src/*.py` 与 shell 入口必须部署在同一个 bin 目录，不混用旧依赖。摘要见 [清单](CONTROLLER_SOURCES.json)。
3. 同步采集工作锁、stop/hold 屏障、watchdog reassert 和只负责采集/索引的 pipeline。不能只复制一个 teslacam.py。
4. 根据实际路径建立 services.json，TOKEN 由文件提供；FRP 和整事件队列默认禁用。该 JSON 是本机配置，不入库。
5. 查清旧 maint/recover/self_recover 的真实入口与调用者。新三个脚本只给迁移提示并退出；不要保留会自动调用旧逻辑的别名、启动项或副本。仓库不会自动扫描或修改用户设备。
6. 原子替换逐文件仍不等于整个目录事务。协调停止、检查源摘要/元数据、备份、替换后复核，失败只恢复本次确认替换的内容，不能覆盖第三方同时修改的文件。

本机曾使用五文件、旧摘要固定的受控更新器，包含元数据保持与失败回滚验证。它只适合当时设备快照，**不作为通用安装工具发布**。特别是原可写恢复入口已收紧为 root 所有，迁移不能照抄任意旧权限。

## 状态迁移

不能复制其他设备的 active_op、boot_id、进程组登记或 clean 凭据；也不能删保护状态来通过 preflight。它们绑定本机实例、映像与操作过程。先看 status，再按明确失败原因走受控 stop/maintain/start。

成功 stop 不等于映像已经检查干净，export_dirty 不因停止就删除。clean-orphans 成功也不等于前一次 recovery_required 已解除，仍需成功 stop 收尾。

若发现 boot_changed，看门狗拒绝是预期保护；此版本没有新增开机自动恢复。重启后的 Root 可用性也没有验证。

## 验收和回退

分别确认：源码/配置来源 → status 完整 → 服务身份/就绪 → 实际 USB 导出 → 车机新录像 → 网页索引/播放。端口可连、旧录像可播不能代替“新录像仍在持续产生”。

新版本失败时保留日志、锁和操作记录，停止推进；必要时在确认所有访问者退出且有备份的前提下回退本次文件/配置，再核对车端录像。不要用删锁、改 active_op 或强制修复介质来制造验收通过。
