# 踩坑记录：为什么做这些保护

以下是本项目调试中实际遇到或用反例复现的问题。修正、测试和未验证部分分开记录，避免把“脚本能跑”写成“录像绝对可靠”。

## 1. stop 只摘 U 盘，网页却还活着

早期控制面只管存储，pipeline 还会自行拉起网页、队列或转发。一个地方 stop，另一个地方又启动，状态无法说明整套软件是否已停止。

处理：服务逐个配置、登记和纳管，统一入口负责启停；发布流水线只采集和索引。旧维护/恢复入口退役，防止绕过控制面。**不能仅凭 LUN 脱离判断整套服务停止。**

## 2. 有短控制锁，仍挡不住 stop 中间插进 start

等待进程退出时不能一直占着控制锁，但只释放锁又让另一操作插入。

处理：完整操作持生命周期锁，短控制锁只保护状态转换。操作身份、父操作摘要和恢复要求持久记录。控制者退出不意味着辅助作业已经退出。

## 3. 锁文件存在不是“锁死”，删除锁文件也不是解锁

删除后新旧进程可能分别锁住不同 inode，看起来都拿到了锁。父进程退出后，继承同一 open file description 的后代也可能继续持锁。

处理：检查真实 flock 竞争与 dev/ino，不删除锁文件制造通过。A 测试分别退出 control、checker、worker，证明最后持有者退出才释放；B 用默认、可继承父 fd 和故意泄漏的阳性对照证明观察器有效。Windows 字节锁替身不能代替 Android 原生证据。

## 4. 按进程名或旧 PID 发信号，会碰到别人的实例

PID 会复用；argv 相似不代表属于本次启动。扫描时的旧 stat 配合稍后 environ 的令牌，也不一定来自同一个实例。

处理：stat → environ 令牌 → post-stat，比较 starttime/pgrp/sid 并锚定组长实例。未知或外组不给信号。status 对未纳管实例只报告，不接管、不清理。

## 5. 周期子进程恰好退出，让健康服务变成 identity_unknown

扫描名单后到读取 `/proc/<pid>/environ` 之间，collect 子进程退出。直接把任何读取失败判未知会周期误报；把所有 OSError 判退出又会吞掉权限故障。

处理：成员三态 ok / gone / bad。只有明确消失、死亡或离组才剔除；确认不了就保守。stat 缺失时再确认 PID 目录，权限不可读仍为未知。全退返回 empty，不能出现零成员 ok。

## 6. 名单变化不能靠“忽略差异”解决

补快照期间成员退出、复用或令牌变化时，旧名单和新 items 容易不一致，甚至导致完整 build 的 KeyError。

处理：逐个复核差异；只把核验通过的实例快照写入 items，从幸存集合构建结果。unmanaged 只引用仍在快照中的成员。增加完整 build 回归，不只测辅助函数。

## 7. --proc-root 传进去了，测试却仍在读真实 /proc

解析器保存键 `proc-root`，消费代码读取 `proc_root`，连字符参数全部静默失效。测试宣称隔离，实际读到真机服务与真实配置。

处理：统一 `replace('-', '_')`；增加 `--sys-block`，所有镜像占用探测走同一个入口。测试必须真的把选项传入，再证明消费层读了指定来源，不能只断言 parse 字典。

## 8. 测试回收没做好，会出现“全绿但后台还有进程”

只 SIGKILL 然后 sleep 既不证明整组退出，也不传播回收失败。CLI 已派生服务但输出超时，还可能没来得及登记责任。

处理：派生前登记 pending；读取本用例目录中的有效登记，先校验再修改。核验身份后发信号，有界等整组退出；失败保留追踪并让套件非零退出。测试不能清真实 active_op 或删共享锁文件。

## 9. 进程在，8081 却被误报为 not_listening

实际网页使用 IPv6 双栈 listener，而状态检查只按 IPv4 查监听归属。浏览器能打开，状态却 ready=false。

处理：按实际 listener 配置 `serve.ready.host`，该环境用 `::1`。P6 先确认 socket 属于核验后的服务组，再测试连接；不能把其他实例占用的端口当成本服务就绪。

## 10. Root shell 找不到 Termux 的 python3

第一次设备 A 测试停在 checker.json 超时，尚未到 A1。根因是包装器用裸 python3，而 Root PATH 没有 Termux bin；检查器实际根本没启动。

处理：control 显式设置 `LOCKCHECK_PY=sys.executable`；包装器用 `${LOCKCHECK_PY:?...}` 并引用完整路径，不静默回退 PATH。失败结果写 checker.result，写盘失败有备用输出，driver 保留 control.out；检查器失败必须让 control 非零退出。**A0 启动失败不能解释成锁语义失败。**

## 11. 编排测试全绿，也可能只是只测了判定函数

曾出现等待不存在的 service.pid、start_one 内部中断丢失责任、launcher 等待失败丢对象、Ctrl+C 绕过 finally 等问题。单独调用 decide_b 的用例发现不了这些路径。

处理：真正执行 run_one，用明确的有效前置上下文注入内存测试，覆盖派生前后、JSON 交付前后、清理异常与等待中断。每个资源单独收尾，一个失败不阻止其余资源处理。

## 12. 前置清单不能只靠“先手动跑过一次”

缺文件、空清单、模块来自包外都应阻止场景启动。为了让假 src 测试通过而自动跳过核验，会削弱真实入口。

处理：清单验证字节数和完整 SHA256、路径边界与实际加载模块来源；默认真实核验，测试显式注入固定上下文。前置拒绝要断言零场景副作用。清单是固定输入完整性检查，不是防恶意篡改的数字签名。

## 13. 包看起来一样，不代表来源真的一样

混入旧正文、测试结果 JSON、缓存、带 BOM 的清单，都会让交付记录和运行代码漂移。ADB 对中文文件名还出现过截断，导致清单缺项。

处理：发行包排除缓存和运行产物，清单显式 UTF-8，实际加载来源与包内 src 一致。设备上的中文文件用 ASCII 暂存名传输后恢复原名再核验。每次重包重新算摘要，不能沿用上一个 ZIP 的结果。

## 14. 旧 boot 的 finished 记录不能授权新 boot 自动导出

用真实函数和内存协作者复现：上一次开机留下的 finished 记录配合 dirty 标记，旧 reassert 能跳过检查直接导出。

处理：校验当前 boot_id，缺记录/旧 boot/未知 boot/未完成操作一律拒绝自动导出。拒绝时不修改记录。实际手机掉电和重启恢复尚未验证，不能把这个防护称为自动恢复能力。

## 15. 旧 recover 转发 start，看似兼容却可能把健康状态弄坏

候选包装器曾打算直接转调 start。重复运行 start 遇到现有服务会拒绝，并可能留下 incomplete，从而影响看门狗。

最终选择：旧入口只输出明确迁移说明并退出 78，既不自动启动，也不恢复旧提权流程。新操作由用户明确使用统一入口发起。

## 16. USB ADB 会随着 USB 切换消失

stop/start 的 down/up 会重枚举，USB 调试通道掉线不能自动解释成脚本结束。

处理：涉及导出变化的受控操作优先使用已建立的 Wi-Fi ADB；物理拔插单独留状态轨迹。安全弹出时 LUN 变空不等于物理断开，必须看到 DISCONNECTED 后 CONFIGURED 才计完整拔插。

## 17. 真实 fsck 会修改测试介质，不能把“修改了”一律当作失败

系统 newfs 工具先因普通文件 ioctl 失败；改用支持文件的工具后，系统检查器又指出 FSInfo 结构差异，并真实修复 next_free。一个要求“字节完全不变”的夹具因此失败，后来在修复后的独立副本复查才干净通过。

处理：保留失败、修复与复查三种证据，不悄悄重写结果；只使用私有小映像，不在生产录像盘试验。检查器 rc、stderr/stdout 与介质变化分别记录，不由“rc=0”推导文件从未改动。

## 18. 测试数字、连通性和文件摘要都有各自边界

195/197 等早期计数含继承重复的方法，是执行数，不是不同场景数；旧套件失败也不能并入候选测试冒充通过。128 项原生回归与锁 A/B、USB 拔插属于不同证据，不混加。

8081 能连接不等于视频播放成功；九模块摘要一致不等于整套仓库逐文件部署；电脑拔插不等于实车拔插；Tailscale 私网入口不证明当时直连。验证说明要一直保留这些差别。

## 当前保留的决定

Windows D 盘提示按所有者决定不再处理；没有依据将其断言为系统 bug，也没有修复生产录像盘。后续价值集中在实车新录像、浏览器播放、实际掉电恢复和长期运行，而非重复排查该提示。
