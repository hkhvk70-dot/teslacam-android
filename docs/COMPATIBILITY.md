## 核心边界：没有稳定快照

当前采集是“车机写映像，手机从只读 loop 挂载视图复制”。只读意味着手机不通过这个挂载修改文件系统，不意味着复制期间内容静止。

Linux mass-storage 文档说明：可写 LUN 的 backing file 虽可读取，主机侧缓存使内容不能视为确定的稳定视图。结合代码，这是仍需验证/改进的一致性风险，不是已经解决的条件。[内核说明](https://docs.kernel.org/usb/mass-storage.html)

较新片段、跨扫描大小稳定、`.part` 重命名及 MP4 元数据校验仅提供筛选；它们不保证缓存刷新、目录/FAT/数据同步，也不证明每一帧完整。

## 录像、删除与维护

- 日常采集不主动摘盘；看门狗重配、维护、系统回收、存储不足和重启仍可能中断录像，不能承诺绝不中断。
- 旧维护的 idle/断电/放电启发式不再作为执行入口；当前维护要求显式 stop、LUN 脱离、访问者排他与门禁检查，不提供定时强修。
- 全量采集器按时间和空间压力删除 `events/TeslaCam` 的副本。被删的副本可能已经是车机滚动删除后唯一剩下的一份。
- 采集器按同名同大小跳过部分文件，同大小内容变化可能漏检；两个采集器共享挂载工作锁，不另行手动启动。
- `_proxy` 生命周期尚未与事件删除完全关联，长期空间占用需要验证和进一步清理设计。

## 设备与文件系统

只在指定车辆、手机和 ROM 上有运行记录。gadget、路径和组合为机型约定，不是通用支持列表。系统需要 Root 及具体 SELinux 权限，Shizuku 不能替代。

代码仅有限探测 FAT32 标记或第一 MBR 分区偏移，不等于完整分区表校验，GPT/exFAT 未支持。线材必须具备数据能力且与录像口匹配，不能由 Type-C 外形推断是否仅充电。
